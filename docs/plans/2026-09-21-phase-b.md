# Phase B: deletion on `update`, and bumping the wrapped Terraform provider

What shipped in #166 and #167, what was deliberately left out, and the limits that
remain. Written after the fact from the reviews that shaped it, so a later reader can
tell a decision from an accident.

## What shipped

**#166 — `update` removes the tool-owned files this generator no longer produces.**
Until now `update` only wrote and seeded. Renaming a tool-owned template left the old
file in the user's project forever: still headered, still compiled, produced by nothing.

**#167 — the two upjet caches are keyed on the provider version, and `update` can bump it.**
The root cause is the caches; the flag only automates the one-line edit that the fixed
caches made safe.

## Design decisions, and what they cost

### The deletion candidate set is `git ls-files`, not a disk walk

This is the whole safety argument, and the first version got it wrong. The original
design said "`update` refuses a dirty tree, so a deletion is exactly as recoverable as
an overwrite." It is not:

```
$ printf '// Code generated by xp-provider-gen. DO NOT EDIT.\n\npackage x\n' > _output/copied.go
$ git status --porcelain              → (empty)      ← requireCleanTree passes
$ git check-ignore -v _output/copied.go → .gitignore:3:_output
$ git ls-files _output                → (empty)      ← never tracked
```

`git status --porcelain` does not see ignored files, so a disk walk would delete a
headered file in `_output/`, `.work/` or `vendor/` and `git reset --hard` would not
bring it back. An exclusion list cannot fix that — a list always misses one. Taking
candidates from `git ls-files` makes the property structural rather than enumerated:
every deletion is necessarily recoverable. It also skips `.git`, every ignored
directory, and the `build/` submodule for free.

Classification stays `core.IsToolOwned` (the content sniff). Using `git grep` as a
second ownership test would recreate the problem the header exists to avoid: two
sources of truth that can disagree.

### No new state in PROJECT

The alternative was recording each render's tool-owned paths in PROJECT and diffing
against it. Rejected: "what was tool-owned last time" is already on disk, in the header.
A parallel list would be a second record that can drift from the first, and existing
projects would have no list, so their first `update` could never delete — a permanent
exception.

### The version bump is a flag on `update`, not a new command

Upjet's `update` finalize pipeline already runs `make generate` before `go mod tidy`,
so regeneration, tidy, `reviewable`, the clean-tree gate and the reviewable `git diff`
all exist. A new command would duplicate that and then have to answer how it differs
from `update`. The cost, which the docs now state: the same diff also carries the
generator refresh and the framework dependency bump. There is no way to bump only the
Terraform provider.

The principle for editing the user-owned `Makefile`, precedent being `go get` editing
`go.mod`: **the tool may change a value in a user-owned file that the tool itself
declared; it does not change that file's shape.** If the Makefile is not the shape it
expects, it aborts rather than guessing.

### Cache keys, not `rm -rf`

The bump could have deleted the stale cache directories. Instead the version went into
both cache keys, in tool-owned files — so plain `update` carries the fix to every
existing project, and a hand-bump is fixed too, without any command knowing a cache
exists. One principle covers both traps: whatever determines the contents belongs in
the key.

## Known limits, accepted deliberately

- **A user-owned file that quotes the header will be deleted**, and re-deleted on every
  `update`, until the quote is removed. Before this change such a file was untouched
  (it was never in the render, so nothing visited it), so this is a genuinely new
  class of victim — small, recoverable from git, and named in the removal message.
  `docs/provider-guide.md` says not to quote the header.
- **Version rollback deletes silently.** An older binary run on a project a newer
  generator touched will delete the newer templates' output; the old `register.go` is
  regenerated without referencing it, so the build may still pass. PROJECT's generator
  version is a git-describe string and cannot be ordered, so there is no semver gate —
  instead the removal message names the generator that last touched PROJECT when it
  differs from the running one.
- **A case-only rename on a case-insensitive filesystem** (macOS default) would make the
  memFS lookup miss the on-disk name and delete the file just written. Exotic; noted,
  not designed around.
- **`applyTerraformVersionBump`'s write failure** is the one path where "no changes were
  made" would have been untrue (`afero.WriteFile` truncates); it carries its own revert
  advice instead. The `runUpdate`-side branch that consumes that distinction has no
  break-test, because nothing calls `runUpdate` directly and it hardcodes `afero.NewOsFs()`.

## Deliberately not done

**Guided migration for seam-signature changes** (Phase B's second item). The six seam
names are a contract and are not changing; what can change is their signatures. No
actual signature change exists to design against, and the project's rule forbids
speculative abstraction. It waits for the change that needs it.

## What the review gate caught

Four gates — design, plan, delivery, and the controller's own runs — each rejected work
that had already passed the one before. The cases worth remembering:

| Gate | What it caught |
|---|---|
| G1 | The safety argument above was false. Proven by planting a headered file under `_output/`, not by reasoning. |
| G1 | A "verified" fact that was not: the tag survey used `grep -E '^v2\.3[5-9]\|^v2\.4'` and silently dropped every v3.x tag. |
| G2 | The blocker's fix had **no test**: with candidates passed in as a parameter, no case could observe where they came from. Both the unit test (real `git init` + `.gitignore`) and the e2e assertion were added because of this. |
| G2 | Three acceptance commands were `no tests to run` + exit 0 — indistinguishable from passing. Acceptance now counts subtests. |
| G2 | One acceptance grep would have failed a correct implementation; another matched the same line before and after the change. |
| G3 | A test that could not fail: the mutual-exclusion case asserted only `err != nil` and was satisfied by an unrelated "working tree is not clean". The implementation was right; the test was theatre. |
| G3 | All four rejection conditions could be disconnected from `RunE` entirely with every test still green — they tested the functions, not the wiring. |

The break-test is what found the last two: for every new check, break the thing it
guards and confirm it goes red. A check that can never fail is not a check.

## Surfaces that prove it

- `TestRemoveOrphans` (7 cases, `dst` a real on-disk FS — `MemMapFs` returns a nil error
  when reading a directory, so the submodule-gitlink case would pass against a wrong
  implementation), `TestTrackedFiles`, `TestReconcileResultPrint`,
  `TestBumpTerraformVersion`, `TestUpdateFlagRejects`, and a test that the rejections are
  wired into `RunE`.
- `e2e-upgrade.sh` removes a template and asserts the orphan is gone and named, while a
  planted gitignored headered file survives.
- `e2e-native.sh` and `e2e-upjet.sh` assert a same-generator `update` prints `removed 0` —
  without it, a generator dropped from the render would delete its output in every
  user's project, silently.
- `e2e-upjet.sh` scaffolds at 2.37.1, bumps to 2.38.0, and checks both Makefile lines,
  both versioned cache directories, the absence of the unversioned ones, and that the new
  docs checkout really is at `v2.38.0` — two directories alone would not prove the
  contents are new, and stale docs raise no error.
- scaffold-diff matched the differences declared in advance, exactly: #166 `AGENTS.md`
  and `docs/ownership.md` in both flavors; #167 native identical, upjet differing in
  `hack/xp-provider-gen.mk`, `apis/generate.go` and `AGENTS.md`.
