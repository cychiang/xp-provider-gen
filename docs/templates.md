# Adding and changing templates

How to add a file to every generated provider, and how the template pipeline
decides what happens to it. Short version: **put a file in the folder** — the
engine discovers it; nothing is wired by hand.

## The three-step flow

1. **Create `pkg/templates/files/<path>.tmpl`.** The path (minus `.tmpl`)
   becomes the file's path inside every generated provider. Use placeholder
   segments where the path depends on the project:

   | Placeholder | Becomes | Example |
   |---|---|---|
   | `GROUP` | the API group | `apis/GROUP/…` → `apis/storage/…` |
   | `VERSION` | the API version | `…/VERSION/…` → `…/v1alpha1/…` |
   | `KIND` | the kind, lowercased | `internal/controller/KIND/` → `…/bucket/` |
   | `IMAGENAME` | the provider name | `cluster/images/IMAGENAME/` → `…/provider-foo/` |

   The special `project/` prefix maps to the provider's root:
   `files/project/Makefile.tmpl` → `Makefile`.

2. **Decide ownership with the header.** Include the line
   `// Code generated by xp-provider-gen. DO NOT EDIT.` in the body (any
   comment syntax that keeps it literal) and the file is **tool-owned**:
   listed as such in the generated `docs/ownership.md` and rewritten by
   `xp-provider-gen update` in every existing provider. Omit it and the file
   is **user-owned**: seeded once, never touched again.

3. **Run `make test`.** The golden ownership test fails with instructions —
   add the output path and your ownership decision to `wantOwnership` in
   `pkg/plugins/crossplane/v2/templates/engine/ownership_test.go`. That
   failing test is deliberate: every new template requires an explicit,
   reviewed ownership decision.

That's all. The file now appears in new scaffolds, in the generated ownership
doc, and (if tool-owned) flows to existing providers on their next `update`.
Run `make e2e-test` before pushing — it scaffolds a real provider and runs its
build and e2e.

## When is a template rendered?

The placeholders in the path decide — nothing else:

- A path containing `GROUP`, `VERSION`, or `KIND` is a **per-kind template** —
  its output depends on a resource, so it renders at `create api` (and is
  re-rendered for every kind by `update`).
- `IMAGENAME` and placeholder-free paths render once, at `init`.
  (`LICENSE` is special-cased as static.)

A template the engine cannot categorize fails discovery loudly — it cannot
silently vanish from scaffolds.

## Template variables

Bodies are Go `text/template`. The standard context provides:

| Variable | Content |
|---|---|
| `{{ .Repo }}` | module path, e.g. `github.com/example/provider-foo` |
| `{{ .ProviderName }}` | provider name derived from the repo, e.g. `provider-foo` |
| `{{ .Boilerplate }}` | the license header block |
| `{{ .Resource.Kind }}`, `{{ .Resource.Group }}`, `{{ .Resource.Version }}` | the kind being generated (API templates only) |

Escape literal `{{` in generated file content (e.g. Makefiles using Go
templates themselves) or switch delimiters — see existing templates for
patterns before inventing one.

## When a file is not enough: generators

A few files can't come from a plain template because they need computed data —
the resource list, the dependency manifest, or the ownership buckets. Their
**bodies** are still template files, under `pkg/templates/generators/`
(deliberately outside `files/`, so auto-discovery never renders them directly);
the Go generator supplies the data:

| File | Body | Data from |
|---|---|---|
| `apis/register.go`, `internal/controller/register.go` | `generators/apis_register.go.tmpl`, `generators/controller_register.go.tmpl` | `register_generators.go` |
| `go.mod` (seed once) | `generators/gomod.tmpl` | `gomod_generator.go` |
| `docs/ownership.md` | `generators/ownership_doc.md.tmpl` | `ownership_doc_generator.go` |

Editing a body is a template change; adding new *data* to one is a Go change.
For a brand-new generated file that needs computed data, model a generator on
the existing ones and add it to `CoreGenerators` (`assembly.go`) so `init`,
`create api`, and `update` all emit it — the ownership doc derives its entry
from the generator automatically. Keep the `DO NOT EDIT` header in tool-owned
bodies: a test fails if it goes missing.

## Rules that keep this safe

- **A fact lives in one place.** Never introduce a second list of template
  paths or ownership decisions; the golden test and the derived ownership doc
  are the only registries.
- **Tool-owned means rewritten.** If users must be able to edit a file, it
  must not carry the header — there is no third state.
- **The ownership header is a substring match.** A user-owned template whose
  body *quotes* the header line becomes tool-owned by accident; phrase docs
  around it (see `AGENTS.md.tmpl` for an example that links instead of quoting).
