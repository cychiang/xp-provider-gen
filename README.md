# xp-provider-gen

[![Test](https://github.com/cychiang/xp-provider-gen/actions/workflows/test.yml/badge.svg)](https://github.com/cychiang/xp-provider-gen/actions/workflows/test.yml)
[![Release](https://img.shields.io/github/v/release/cychiang/xp-provider-gen)](https://github.com/cychiang/xp-provider-gen/releases)
[![Go Reference](https://pkg.go.dev/badge/github.com/cychiang/xp-provider-gen.svg)](https://pkg.go.dev/github.com/cychiang/xp-provider-gen)

`xp-provider-gen` is a Go CLI that scaffolds [Crossplane](https://crossplane.io) providers on
crossplane-runtime v2, and keeps them up to date as the generator improves. It scaffolds two
flavors. A **native** provider is one where you write the reconcile logic in Go. An **upjet**
provider wraps a Terraform provider, and its types and controllers are generated from the
Terraform schema.

The project is pre-1.0. A minor release can break flags, commands, or the generated layout, and
its release notes say what to change. v0.4.0, for example, removed `update --adopt`.

## What you get

- `update` refreshes the tool-owned files of an existing provider (wiring, registration,
  `main.go`, and framework dependency versions) and never touches the code you wrote.
- A `// Code generated by xp-provider-gen. DO NOT EDIT.` header marks each tool-owned file.
  Every provider gets a generated `docs/ownership.md` that lists which files are yours.
- The generated provider declares the Crossplane v2 `safe-start` capability. Management
  Policies are on by default, change logs are behind `--enable-changelogs`, and the controllers
  record managed-resource metrics.
- `make e2e` in the generated provider deploys it to a kind cluster and runs uptest and
  chainsaw tests. It needs Docker. On a native provider, each `create api` seeds the kind's
  example manifest (the uptest input) and a chainsaw pause test. On upjet, you write the example
  manifest after `make generate`.
- One version manifest pins the provider's dependencies. Renovate bumps it in this repo, and
  `update` applies it to your provider.

## Install

Install with Go 1.26.11 or later:

```bash
go install github.com/cychiang/xp-provider-gen/cmd/xp-provider-gen@latest
xp-provider-gen version
```

Prebuilt binaries for Linux, macOS, and Windows, with checksums, are on the
[Releases](https://github.com/cychiang/xp-provider-gen/releases) page. A multi-arch container
image is published as `ghcr.io/cychiang/xp-provider-gen`. To build from source:

```bash
git clone https://github.com/cychiang/xp-provider-gen.git
cd xp-provider-gen
make build
export PATH="$PWD/bin:$PATH"
```

`init` needs Git and network access. It clones the `crossplane/build` submodule and downloads
Go modules. `make build` in a generated provider also needs Docker.

## Scaffold a native provider

Run `init` in a new, empty directory, not inside the xp-provider-gen clone:

```bash
mkdir provider-awesome && cd provider-awesome
xp-provider-gen init --domain=example.com --repo=github.com/example/provider-awesome
xp-provider-gen create api --group=compute --version=v1alpha1 --kind=Instance
xp-provider-gen create api --group=storage --version=v1 --kind=Bucket
make reviewable
```

`init` runs `make generate` and `make reviewable` itself, and `create api` runs `make generate`.
The last `make reviewable` checks the finished scaffold again. It needs no Docker.
To write the reconcile logic, follow [the tutorial](docs/tutorial.md). It builds a complete
provider and runs it on a local kind cluster in about thirty minutes.

## Scaffold an upjet provider

```bash
mkdir provider-k8s && cd provider-k8s
xp-provider-gen init --domain=example.com --repo=github.com/example/provider-k8s \
  --upjet --terraform-provider=hashicorp/kubernetes --terraform-provider-version=2.38.0
xp-provider-gen create api --group=core --version=v1alpha1 --kind=ConfigMap \
  --terraform-resource=kubernetes_config_map
make generate
make reviewable
```

An upjet scaffold does not compile until `make generate` runs. `make generate` downloads
Terraform and the provider schema, so it needs network access and can take a few minutes the
first time. Every upjet `make` prints two warnings about the `go.generate` target. They are
expected. To test a kind, copy its generated example from `examples-generated/` to
`examples/<group>/<kind>.yaml`, as the `create api` output says, then run `create-test`.
[docs/upjet-provider.md](docs/upjet-provider.md) covers credentials, deployment, and
bumping the Terraform provider.

## Commit history while you scaffold

`init` makes one commit, `Initial commit`. Each `create api` amends that commit
(`git commit --amend`) until you make a commit of your own, so a new provider starts with one
commit. Make your own first commit before you push. Otherwise the next `create api` amends a
commit you already pushed, and you need a force-push. After your first commit, each
`create api` adds a new commit. Every `create api` stages the whole working tree (`git add .`).
Commit or stash unrelated edits first, or they end up in the commit that `create api` makes or
amends.

The commits `init` and `create api` make use your git identity. `init --git-name` and
`--git-email` replace `user.name` and `user.email` for the commit `init` makes, also in a
repository that already exists. A `create api` amend keeps that author and records your git
identity as the committer. A name or email that neither the flags nor git's `user.name` and
`user.email` supply falls back to `xp-provider-gen <xp-provider-gen@example.com>`. `init` writes
no identity into the repository's `.git/config`, so your own commits keep yours.

## Commands

The CLI has four scaffolding commands: `init`, `create api`, `create-test`, and `update`.
`xp-provider-gen <command> --help` lists every flag.
[docs/provider-guide.md](docs/provider-guide.md) describes what you edit in a native provider and
how to upgrade it. [docs/upjet-provider.md](docs/upjet-provider.md) does the same for upjet. The
[xp-provider-gen skill](.agents/skills/xp-provider-gen/SKILL.md) is a reference
for each command, written for coding agents.
